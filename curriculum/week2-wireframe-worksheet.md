# Week 2 Wireframe Worksheet

**Session:** Wednesday, July 22, 2026 — UX critique and Cross-functional Build Lab
**Gate:** Friday, July 24, 2026 — MVP/Prototype v1
**You bring:** this worksheet, completed, plus your wireframe frames.

A wireframe is not a design. It is a decision record. It is where you decide what your product
does *not* do. Bring boxes and labels — no colours, no fonts, no logos. Paper and a phone photo is
acceptable and always has been.

---

## Step 1 — Lock the scope before you draw anything

Copy these from your MVP Scope Sheet. If you cannot fill this in, stop and finish that sheet first.

| Field | Your answer |
|---|---|
| The one user | |

| Where the flow ends (the moment they get value) | |
| The single sentence that describes the whole flow | |

**Rule:** if you cannot write the last row as one sentence with no "and also", your scope is still
too big. Cut until you can.

---

## Step 2 — List the screens

Write every screen the user passes through between "starts" and "gets value". Number them in order.
Most 4-week MVPs need between three and six.

| # | Screen name | Why the flow cannot work without it |
|---|---|---|
| 1 | | |
| 2 | | |
| 3 | | |
| 4 | | |
| 5 | | |
| 6 | | |

**The cut test:** for each screen, ask *"if I delete this, does the user still get to the value
moment?"* If the answer is yes, delete it. Settings pages, profile pages, About pages, dashboards,
and onboarding tours almost always fail this test in v1.

**Screens you are probably about to add and should not:** admin panels nobody outside your team
sees on Demo Day, notification preferences, multi-language, dark mode, referral systems, anything
described as "phase 2 but let me just put a placeholder".

---

## Step 3 — Draw each frame

One frame per screen. For every frame, answer all six rows. An unanswered row is an unfinished
screen.

| Question | Answer |
|---|---|
| Screen name and number | |
| The user arrives here from | |
| The one thing they must understand within 3 seconds | |
| Everything they must see to make their decision | |
| **The single primary action** (one per screen) | |
| Where that action sends them | |
| What is real, and what is faked or done by hand behind it | |

**One primary action per screen.** If a frame has two buttons of equal weight, you have not decided
what the screen is for. Secondary actions are allowed but must look secondary.

**Label with real content.** Write "Ota to Berger — ₦2,400" not "Text goes here". Fake data hides
problems that real data exposes.

---

## Step 4 — Declare what is manual

Most honest early MVPs have a human behind the curtain. This is a legitimate build strategy, not
cheating — but it must be declared, and you must know your limits.

| Step in the flow | Automated or manual | Who does it by hand | Breaks at how many users/day? |
|---|---|---|---|
| | | | |
| | | | |
| | | | |

**You will be asked this at the gate.** A founder who says "assignment is manual, it's me on
WhatsApp, it breaks past about 20 orders a day" scores higher than one who implies everything is
automated. Overstating what is built is the fastest way to fail the gate.

---

## Step 5 — Handle the three dead ends

Every flow has these. Sketch them as small frames or write them as sentences.

| Situation | What the user sees | What they can do next |
|---|---|---|
| Nothing here yet (empty state) | | |
| Something went wrong | | |
| We cannot serve you (out of area, unavailable, closed) | | |

A product that only works when everything goes right is a demo, not an MVP. The third row matters
most — telling someone honestly that you cannot help them keeps them as a future customer.

---

## Step 6 — Choose your build path

You do not need to be able to code, and you do not need a developer to reach August 3.

| Path | Best when | Realistic in 13 days? |
|---|---|---|
| No-code app builder over a database | You are non-technical and the flow is forms plus records | Yes |
| Form plus spreadsheet plus manual ops | The flow is intake and fulfilment, and you run ops yourself | Yes, comfortably |
| Clickable Figma prototype | The product is visual and the value is the experience | Yes |
| AI-assisted code build | You can read code and debug when it breaks | Sometimes — have a fallback |
| Custom code by a developer you have not hired yet | Never, in 13 days | No |

**Write your choice, and your fallback:**

- Build path: ______________________________
- If it is not working by Monday, July 27, I fall back to: ______________________________

The fallback is not pessimism. Every founder who has shipped on a deadline had one.
